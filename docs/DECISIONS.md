| D9 | Evaluation strategy for all subjects | Stratified subject sampling. NLP metrics and expert rubric run on three representative subjects: one quantitative (math), one mixed (science), one open ended (history or literature). Gold references and subject competent raters per sampled subject. NLP similarity metrics are paired with critic correctness accuracy per subject type, since ROUGE, BLEU and BERTScore measure similarity to references, not factual correctness. Behavioral metrics (NGS, ATT, TCV, HSR) and CAR are subject agnostic and run on whatever subjects the pilot uses | Evaluating every possible subject is infeasible. Sampling one subject per subject type gives generalization evidence. Similarity metrics alone cannot detect factual errors in open ended content | 2026-07-08 |
| D10 | Use case model revision | Fig 1 now shows actor goal use cases only: 4 student (View History, Browse and Select, Solve Problems, Interact with Teachable Agent) and 5 teacher (Create Program, Publish to Distribution List, View Performance Evaluation, Monitor Student Analytics, Review Content with Modify Content extend). Internal automation (generation, self correction, scoring, memory learning, affective detection, scaffolding) is no longer modeled as use cases and lives in FR2, FR3, FR4, FR6, FR10, FR12 unchanged | Standard UML practice: use cases model actor goals, not internal system behavior. No feature was descoped | 2026-07-08 |
| D11 | Answer protection storage split | Each exercise persists as a student safe exercises doc plus a teacher only exerciseSolutions doc with the same id. Student read gating uses assignedStudentKeys arrays denormalized at publish time | Firestore rules cannot hide fields of a readable doc, and list rules must be provable from query filters, so a get based rule would reject student queries. Deliberate improvement over the book flat exercise doc, see docs/API_CONTRACT.md | 2026-08-15 |
| D12 | Science subject type for the critic (Q12) | open_ended, claim verification | D9 calls science a mixed subject but the critic strategy map is two valued. The curated elementary science standards are conceptual, so claim verification fits. A calculation heavy science unit would get claim checking rather than an independent solve, revisit if the pilot needs one | 2026-11-18 |
| D13 | NFR2 re-scope (Q10) | Split into NFR2a, interactive tutor turn p95 <= 15s, and NFR2b, curriculum generation p95 <= 900s | The Phase A NFR2 put 15s on generate plus score plus self correct. A package is roughly 4000 to 5500 output tokens across 7 sequential model calls, so 15s is unreachable without removing the critic loop or the lesson content. Measured DEV runs: about 190s for a single pass, 253s to 673s end to end (evaluation/results/dev_runs/summary.json). The 15s figure is kept where responsiveness is actually felt, the student facing tutor turn. Both figures are Phase B targets, not results (R1). Accepted 2026-11-19 as the Phase B target. The Phase A book still specifies the original single NFR2, so the Phase B book and the defense must state this deviation and its rationale outright rather than leave a reader to find it in thresholds.yaml | 2026-11-18, accepted 2026-11-19 |
| D14 | Critic wrong_answer confirmation (Q11) | Two guards, both resting on the deterministic comparison. (a) A guard mismatch is re-solved blind a second time and kept only when that solve also disagrees with the stated answer. (b) A wrong_answer the critic raises in pass 2 is dropped when the independent solve agreed on that exercise, and a rejection whose only reason was dropped becomes an approval. | On the difficulty 5 dev brief 2 of 3 final wrong_answer flags came from errors in the critic's own blind solve, marking a correct unit unapproved. Validating (a) showed a second path: the critic can invent a divergence in pass 2 against its own solve, where no guard mismatch exists to confirm, so (b) was added. An empty rejection would ask lesson design to fix nothing. Dropping needs positive agreement, an undecidable comparison keeps the flag, so no real error is traded away. Residual risk: a critic that repeats the same error in both blind solves keeps a false flag, quantified in Step 5.4. Evidence in docs/prompt_log.md | 2026-11-18 |
| D15 | Bot transport (Q6) | Student to FastAPI over SSE for the live turn, each completed turn mirrored to Firestore for persistence and analytics | The book mentions both a FastAPI path and a Firebase listener. SSE streams tokens as they are generated, which is what NFR8 asks for. A Firestore listener would show nothing until the whole hint is written, leaving a waiting child with a blank box. Mirroring afterwards keeps the full transcript for FR13 history and Phase 5 analytics. Step 3.5 implements the live SSE turn, the Firestore mirror lands with the chat UI in Step 4.6, its first consumer, since it needs a tutorTurns collection with its own security rules | 2026-11-18 |
| D16 | Tutor session state (Q7) | In process per session StudentModel, no Redis. Kept behind a small store interface so a shared backend can be swapped in | Redis is not required by the committee. For a single server pilot of 10 or more students, in process state is sufficient. Its failure modes, loss on restart and incorrectness across multiple worker processes, are acceptable for the pilot and are the reason the interface exists. Redis or equivalent is the production swap, recorded as such rather than built | 2026-11-18 |
| D17 | FR4 scoring split (Step 3.6) | Three tiers. Inline per request: ROUGE-L only, pure Python, Hebrew preserving tokenizer, against the nearest same subject gold reference, and never across subjects. Post response background task: BERTScore on xlm-roberta-large (D6), patched onto the module doc through a dotted field path, simply absent when the scorer is not installed. Offline harness only (Step 5.3): BLEU. Every score travels with the reference unit it was measured against and whether that unit is teacher validated | BERTScore needs torch and a model load, and bert-score is deferred to Phase 5 by BUILD_GUIDE Step 0.1, so an inline BERTScore would have no scorer to call and, once installed, would spend more wall time than the pipeline it is grading. ROUGE-L is milliseconds. The rouge_score default tokenizer replaces every non Latin character with a space, so Hebrew tokenizes to nothing and every score would have been a silent 0.0 rather than an error, which is why the tokenizer is named in TOKENIZER_ID and pinned by a test. Hebrew prefix letters stay attached, so the inline number undercounts matches and is a conservative lower bound. BLEU stays offline so the sacrebleu tokenization choice is made and recorded in one place. A similarity number is unreadable without its reference, and the only reference unit in the repo is still DRAFT, so reference_validated stops a draft backed diagnostic from being read as a metric (R1). Scoring never fails a generation: a draft the scorer cannot read comes back unscored | 2026-11-19 |
