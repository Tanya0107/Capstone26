| D14 | Critic wrong_answer confirmation (Q11) | Two guards, both resting on the deterministic comparison. (a) A guard mismatch is re-solved blind a second time and kept only when that solve also disagrees with the stated answer. (b) A wrong_answer the critic raises in pass 2 is dropped when the independent solve agreed on that exercise, and a rejection whose only reason was dropped becomes an approval. | On the difficulty 5 dev brief 2 of 3 final wrong_answer flags came from errors in the critic's own blind solve, marking a correct unit unapproved. Validating (a) showed a second path: the critic can invent a divergence in pass 2 against its own solve, where no guard mismatch exists to confirm, so (b) was added. An empty rejection would ask lesson design to fix nothing. Dropping needs positive agreement, an undecidable comparison keeps the flag, so no real error is traded away. Residual risk: a critic that repeats the same error in both blind solves keeps a false flag, quantified in Step 5.4. Evidence in docs/prompt_log.md | 2026-11-18 |

| D17 | FR4 scoring split (Step 3.6) | Three tiers. Inline per request: ROUGE-L only, pure Python, Hebrew preserving tokenizer, against the nearest same subject gold reference, and never across subjects. Post response background task: BERTScore on xlm-roberta-large (D6), patched onto the module doc through a dotted field path, simply absent when the scorer is not installed. Offline harness only (Step 5.3): BLEU. Every score travels with the reference unit it was measured against and whether that unit is teacher validated | BERTScore needs torch and a model load, and bert-score is deferred to Phase 5 by BUILD_GUIDE Step 0.1, so an inline BERTScore would have no scorer to call and, once installed, would spend more wall time than the pipeline it is grading. ROUGE-L is milliseconds. The rouge_score default tokenizer replaces every non Latin character with a space, so Hebrew tokenizes to nothing and every score would have been a silent 0.0 rather than an error, which is why the tokenizer is named in TOKENIZER_ID and pinned by a test. Hebrew prefix letters stay attached, so the inline number undercounts matches and is a conservative lower bound. BLEU stays offline so the sacrebleu tokenization choice is made and recorded in one place. A similarity number is unreadable without its reference, and the only reference unit in the repo is still DRAFT, so reference_validated stops a draft backed diagnostic from being read as a metric (R1). Scoring never fails a generation: a draft the scorer cannot read comes back unscored | 2026-11-19 |

| D19 | UI harnesses drive an authenticated page through its own handlers, never through CDP input (Step 4.2 follow up, amended in Step 4.3) | Every scripted UI check enters text by calling the `HTMLInputElement` or `HTMLTextAreaElement` `value` setter and dispatching a bubbling `input` event, the way `setField` in `scripts/dev_goals_screen_demo.mjs` does, and clicks an element by calling its own `click()` through `page.$eval`. No harness may use `page.type`, `page.keyboard` or `page.click` on an authenticated page. Sign in on `/login` is unaffected and still uses real input | CDP key events are not delivered to an authenticated page in this rig, while mouse events, `Input.insertText`, focus and the DOM are all healthy there. Measured on `/teacher/create` in one run: 0 `keydown` from three separate key dispatch paths, `mousedown` delivered, `insertText` delivered, the textarea focused in 30 of 30 samples over 3s with 0 blur events and 0 node swaps, one frame, no long tasks, no console errors. No page code can suppress an event that never arrives, and a field that holds focus with no blur and no node swap is not being remounted, so the missing channel is the rig's. This was first recorded as an application defect that would make FR1 unusable, which was wrong and is withdrawn in docs/prompt_log.md. The rule exists so Steps 4.3 to 4.6 do not rediscover it: a harness that drives an authenticated page through CDP measures the rig and not the product. Amended in Step 4.3, which found clicks affected as well, not only keys: `page.click` on the publish button changed nothing, no state change and no Firestore query, while that same button's own `click()` opened the dialog and loaded all 12 students. The button was enabled, inside the viewport and topmost at its own centre, so occlusion and disabled state are both ruled out. Delivery is intermittent rather than absent, since the Step 4.2 demo's `page.click` calls did work, which is why the rule is to not depend on CDP input here at all rather than to work around it case by case. Residual, not a blocker: the exact rig mechanism is unnamed and no one has yet typed on a real keyboard on one of these pages | 2026-11-21 |

Two concrete failures followed from that, which is why it was added rather than only noted. | D21 | Student progress, answer storage and scaffolding (Step 4.4) | Four decisions, all forced by the Fig 4 schema rather than chosen freely. (a) A studentProgress document has a derived id, assignmentKey__studentKey, so a student has exactly one per assignment. (b) currentExerciseOrder counts submitted exercises and nothing else, which makes it simultaneously the resume point, the progress figure and the gate on moving forward. (c) Answer text is buffered in localStorage and is never written to Firestore, because no collection in the schema holds it. A submission is therefore the progress advance, and lib/student/answerBuffer keeps its own durable queue of unacknowledged advances. (d) ScaffoldingSteps discloses one step per request and starts closed. | On (a): the alternative is a query for the student's progress on this assignment followed by a create or an update, which needs an index, adds a round trip before the first write and can produce two documents under a race. A derived id makes the write an idempotent upsert, which is what lets a queued offline advance be replayed any number of times safely. The rules already gate on studentKey inside the document, so the id carries no authority and the id scheme is not a security assumption. On (b): three jobs on one number sounds like overloading until the offline case is considered, where a replayed write and a screen that moved on must agree about what has been done. A separate view pointer would drift from the document and a student would come back to the wrong exercise. The number is a count, so a merge write of a stale lower value cannot move it backwards once Math.max is applied at the call site. On (c): BUILD_GUIDE Step 4.4 asks for localStorage answer buffering and the book Fig 4 schema has no answers collection, so storing answer text would mean inventing a collection, its security rules and its contract after the Phase 2 freeze. It is kept local deliberately rather than by oversight, and the consequence, that a teacher cannot read what a student wrote, is recorded as Q14. The durable queue exists for a narrower reason: the Firestore SDK already retries a write made offline, but its queue is in memory, so a reload while offline loses the submission silently and the student's progress goes backwards with no error anywhere. Also on (c): the progress document is created when the workspace opens rather than on the first submission, so startedAt means the student opened the unit, which is what FR13 history and the Phase 5 time on task figures need it to mean. On (d): a child who can see the whole breakdown at once has been handed a recipe, not a scaffold, which is the opposite of FR10. The revealed count lives in the workspace rather than in the component so Step 4.5 can hang help seeking telemetry on it without touching the pedagogy. Verified in evaluation/results/dev_runs/student_workspace_demo.json, where a teacher publishes through the real Review Dashboard in one page and the unit appears in the signed in student's other page with no reload, the unit is then solved end to end, and an answer typed with the connection cut is shown to be on disk and to survive a reload. | 2026-11-24 |
| D22 | Telemetry beat shape, timestamps and what counts as help (Step 4.5) | Five choices. (a) One telemetryEvents document per heartbeat, where attSeconds is the active time of that single 15s interval and hsrcCount the help clicks inside it, rather than a running total per exercise. (b) timestamp is the client clock at the beat, not a serverTimestamp. (c) A beat id is deterministic, studentKey__sessionNonce__sequence, and is also the document id. (d) Idle time is excluded by a beat not happening at all, never by subtracting it afterwards. (e) Revealing a scaffold step does not increment hsrcCount. | On (a): backend/app/core/telemetry.py states that heartbeats farther apart than IDLE_CUTOFF_SECONDS count as idle, which the server can only judge if it sees the individual beats and their spacing, and compute_hsr sums hsrcCount across events, which needs per event counts. A running total would defeat both at once, since every beat would restate the same seconds and summing the counter would multiply every click by the number of beats after it. On (b): a serverTimestamp is written when the write arrives, so a beat buffered through an offline stretch would arrive stamped with the moment of the reconnect. Every gap the idle cutoff exists to find would collapse to nothing and idle time would quietly be counted as active. Only the spacing between one student's own beats is ever compared, so clock skew between devices costs nothing, while clock trust is the real price: a student could in principle forge their own figures. These numbers are behavioural research data supporting ATT, TCV and HSR and are never a grade, which is what makes that acceptable. On (c): the security rules make the log append only and refuse a student reading it back, so the client can neither check what is already there nor repair a duplicate. A deterministic id turns the replay of a buffered beat into a permission-denied on an id that already exists, which is a refusal rather than a double count. Measured both ways, in firebase/rules.test.ts and again through the REST API with a real student token in the demo. The cost is that a genuine rules problem looks identical and also drops the beat, which is the better failure: the alternative is a queue that retries for ever. A failed batch is retried as individual writes for the same reason, since a batch is atomic and one stale id would otherwise refuse the fresh beats beside it. On (d): subtracting idle time needs a definition of when it started, which the client cannot know without logging the absence of activity, so the simpler rule is that a 15s interval with no keystroke and no pointer event earns nothing. Verified in evaluation/results/dev_runs/telemetry_session.json: a 251s session accrued 135s, excluding 116s, and the beat timestamps read 15, 15, 15, 105, 15, 15, 15, 15 seconds apart, so the 95s idle stretch is both absent from the accrual and visible to the server cutoff as a 105s gap. On (e): a hint request is help seeking in the literature behind HSR, so counting a scaffold reveal would be defensible. It is not counted because the frozen contract has one hsrcCount and no event type, so tutor help and hint reveals would land in the same number with no way to separate them, and an HSR that mixes two channels cannot be read. BUILD_GUIDE Step 4.5 names the Ask the tutor click and Step 4.6 verifies the increment there. The revealed count D21 put in the workspace stays available if the team later wants a second channel, which would need a contract change rather than a quiet reinterpretation of this field. Residual: IDLE_CUTOFF_SECONDS carries a TODO to calibrate and is still the skeleton's 90. Nothing in Phase 4 depends on the exact value, and Step 5.2 computes ATT with it, so it should be calibrated from the pilot's own telemetry before any ATT figure is reported. | 2026-11-25 |
